01

The organization

Riverside County consolidated its citizen-facing services under a single Department of Citizen Services. A small central AI Platform Team builds and governs agents; the people who actually use them are non-technical caseworkers, clerks, and program officers spread across five departments.

Leadership set three non-negotiables, and those mandates are exactly what put the identity and governance capabilities on stage:

  • No citizen PII leaves the county boundary — sensitive workloads run on a data-resident model tier, and every backend datastore is encrypted at rest.
  • Every agent action is audited — a complete, reviewable trail for compliance.
  • Agents touch only what their role — and their MCP scope — allows — access is scoped by agent identity down to individual tools, not blanket credentials.

04

Technology stack

Two agent runtimes on purpose — proving Agent Manager's governance layer (roles, scopes, guardrails, evaluators, pipelines) applies identically regardless of what the agent is written in. All three MCP servers are Python for consistency, since MCP is transport-level and language-agnostic — the Ballerina agent talks to a Python-hosted MCP server over the same protocol a Python agent would use.

Citizen Inquiry Agent
Python 3.11 LangChain

One image, 5 instances differing only by injected env vars (MCP_API_KEY per department namespace).

Permit & Licensing Agent
Python 3.11 LangChain

Same stack as Citizen Inquiry; 2 instances from one image, different prompt-template config.

Case Management Agent
Ballerina

Deliberately different runtime, native MCP client — proves governance is language-agnostic.

Unified KB MCP Server
Python FastMCP

Embedded local vector store, namespace-partitioned per department, encrypted at rest.

Permit DB MCP Server
Python FastMCP

Embedded local SQLite, SQLCipher (AES-256)-encrypted, dedicated to Permit & Licensing.

Case Management MCP Server
Python FastMCP

Embedded local SQLite, SQLCipher-encrypted, 7 tools exposed / 3 scoped in.

Packaging is one container per agent kind and per MCP server, built via amp:agent:build and promoted through the pipelines in §02. MCP servers are platform infrastructure the Admin manages (amp:mcp-server:*) — they are not redeployed per instance.

06

Instantiation & MCP architecture

Instances

  • Citizen Inquiry Agent → 5 instances, one per citizen-facing department. Same image, same Unified KB MCP server, but each carries a different MCP_API_KEY — the server maps that key to one department namespace, so dept=social-services cannot read the dept=tax-revenue partition even though the tool call looks identical.
  • Permit & Licensing Agent → 2 instances (Building Permits and Business Licenses), both pointed at the same dedicated Permit DB MCP server, each with its own permit-type prompt template.
  • Case Management Agent → 1 instance, Social Services, deployed to Development on a cloud model and to Production pinned to the data-resident AWS GovCloud Bedrock tier.
  • One external agent registered — the county's legacy contact-center chatbot — attached to the gateway with a redirect policy forwarding its old endpoint to the new Contact Center Citizen Inquiry instance.

Net effect

3 kinds become ~9 running instances (5 + 2 + 1 + 1 external).

One shared KB, two dedicated encrypted DBs

Permit & Licensing and Case Management each get their own dedicated MCP server for database management — separate processes, separate encrypted stores, never shared with each other or with the KB server. Citizen Inquiry's knowledge, by contrast, is deliberately shared, partitioned by namespace.

MCP serverServesData storeEncryption
Unified KB MCP ServerCitizen Inquiry (5 instances)Embedded local vector/document store, 1 namespace per departmentEncrypted at rest
Permit DB MCP ServerPermit & Licensing (2 instances)Embedded local SQLite — applications, fee schedulesSQLCipher AES-256
Case Management MCP ServerCase Management (1 instance)Embedded local SQLite — case records, citizen profilesSQLCipher AES-256

All three run locally inside the MCP server process itself — no external managed database. The encryption key for each is a amp:git-secret entry only the Platform Admin can create or rotate (§03).

Unified KB namespacing

ToolEffect
kb_search(query)Semantic search over the caller's namespace
kb_read(doc_id)Fetch a specific article from the caller's namespace
kb_write(doc_id, content)Create or update an article in the caller's namespace
kb_list_sources()List source documents the caller's namespace was built from

Same server, same four tools, five namespaces — isolation enforced entirely by which API key resolved to which namespace. mcp-ratelimit is applied per tool so one namespace's traffic can't starve another's.

Connecting an agent to its MCP server

Every agent instance authenticates with an API key over the MCP server's URL. At deploy time Agent Manager injects two env vars into the instance:

MCP_SERVER_URL MCP_API_KEY

Identical URL for all 5 KB instances, distinct per dedicated DB server. For Citizen Inquiry the key resolves to a namespace server-side; for Permit & Licensing and Case Management it's the sole credential the dedicated server accepts at all. This is what "a different environment credential per department" means in practice.

07

MCP tool scoping — the Case Management Agent is the demo

The dedicated Case Management MCP server exposes seven tools against the county case system:

case_search case_read case_notes_write case_status_update citizen_profile_read citizen_profile_write case_close

The Case Management Agent's identity is granted a scope containing exactly the first three. Everything else — including citizen_profile_read beyond the assigned case — is outside the agent's scope.

The centerpiece

Live in a trace, the model (running inside the Ballerina agent) attempts citizen_profile_read on a citizen outside the caseworker's assignment. The call is denied by MCP scope enforcement before it reaches the encrypted store, and the denial is written to the audit log — a clean policy rejection, not a crash or a hallucinated success.

amp:scope:read (everyone) vs. amp:scope:create/update (Admin only) is what makes that scope Dana's-to-change-not-Marcus's-to-change, tying §03's RBAC directly to this MCP boundary.

08

Identity & on-behalf-of

  • Auto-provisioned Agent ID for every instance the moment it is created.
  • OAuth2 on-behalf-of — when caseworker Joan runs the Case Management Agent, it accesses records as Joan, scoped to her assigned cases — never with god-mode access. Combined with §03, Joan's own scopes (Agent Operator — no case-system access of her own) plus the agent's MCP scope (§07) form two independent boundaries stacking.
  • Third-party auth server integration — the county's existing IDP fronts agent ingress; the Case Management MCP server validates the on-behalf-of token via Opaque Token Auth (RFC 7662 introspection) before honoring any of the three scoped tools, on top of the API-key check in §06.

The visual that lands

Run the same Case Management Agent as two different caseworkers and watch case_search return two different case lists — same instance, same MCP scope, two identities, two data views.

09

LLM proxy & guardrails

An Agent Manager LLM Proxy sits in front of every provider — agents never call a model endpoint directly.

ProviderBound toResidency
Azure OpenAI (gov region)Citizen Inquiry, Permit & LicensingCloud
AWS Bedrock (GovCloud) via OpenAI→Bedrock Transformer, SigV4-signedCase ManagementData-resident

Kept deliberately small — 3–4 guardrails per agent kind, chosen for what actually matters for that kind's risk profile, not the full policy catalog:

Agent kindGuardrails
Citizen Inquiry AgentPII Masking Regex, Content Length Guardrail, Prompt Decorator (branding)
Permit & Licensing AgentJSON Schema Guardrail, Word Count Guardrail, URL Guardrail
Case Management AgentPII Masking Regex, Opaque Token Auth, mcp-ratelimit

Plus two platform-level policies not tied to a single agent kind: AWS Authentication (SigV4/STS) signs the Case Management LLM proxy's calls to Bedrock GovCloud, and redirect migrates the legacy chatbot's traffic to the new Contact Center instance at the gateway.

10

Evaluators — 12 selected, mapped by agent kind

Running all 24 available evaluators on every trace is unnecessary here; 4 per agent kind proves the observability story without drowning the dashboard.

Agent kindEvaluators
Citizen Inquiry AgentLatency Performance (rule), Length Compliance (rule), Helpfulness (judge), Tone (judge)
Permit & Licensing AgentStep Success Rate (rule), Sequence Adherence (rule), Instruction Following (judge), Completeness (judge)
Case Management AgentTool Coverage (rule), Content Safety (rule), Groundedness (judge), Safety (judge)

Load-bearing, not filler

Tool Coverage on Case Management directly measures whether the agent stayed inside its three-tool MCP scope (§07) — a scoping violation shows up as a failing evaluator score, not just an audit-log line. Content Safety is the automated backstop behind the PII Masking Regex guardrail (§09) — belt-and-suspenders on the same risk.

Rule-based evaluators are free and run on every trace; judge evaluators run on a sample using the org's own LLM proxy. Score visibility follows §03: amp:monitor:score-read for Admin/Developer/Auditor, amp:monitor:score-publish for Admin only — the gate the Case Management pipeline (§02) depends on.

11

Sandboxing

Any code execution the Permit & Licensing Agent needs (fee calculations, form validation) runs inside a hardened sandbox with no access to host, network, or filesystem — one clean scenario proving agent-generated code cannot exfiltrate citizen data even if it wanted to.

12

Development plan

Sequenced so every phase produces something demoable, rather than a big-bang integration at the end.

Phase 0

Platform foundations

  • Stand up the org, 3 environments, 4 roles + scopes, invite the 5 personas.
  • Create the amp:git-secret entries for the two SQLCipher encryption keys.
Phase 1

MCP servers

  • Build the Unified KB MCP Server (Python/FastMCP) — namespace-partitioned store, seed docs per department.
  • Build the Permit DB MCP Server (Python/FastMCP) — SQLCipher-encrypted SQLite, seed permit/fee data.
  • Build the Case Management MCP Server (Python/FastMCP) — SQLCipher-encrypted SQLite, seed case records, all 7 tools.
  • Register all three (amp:mcp-server:create); mint per-consumer API keys.
Phase 2

Agent kinds

  • Build Citizen Inquiry Agent (Python/LangChain) with env-injected MCP_SERVER_URL/MCP_API_KEY; publish to catalog.
  • Build Permit & Licensing Agent (Python/LangChain) against the dedicated Permit DB MCP + external State ID Verification MCP.
  • Build Case Management Agent (Ballerina) against the dedicated Case Management MCP; wire the 3-tool scope and OAuth2 on-behalf-of.
Phase 3

Instantiation & pipelines

  • Instantiate Citizen Inquiry × 5, Permit & Licensing × 2, Case Management × 1.
  • Register the external legacy chatbot and its gateway redirect policy.
  • Stand up the 3 deployment pipelines and their promotion gates.
Phase 4

LLM proxy & guardrails

  • Register Azure OpenAI and AWS Bedrock GovCloud behind the LLM Proxy; wire the Transformer + AWS Authentication.
  • Attach the 3–4 guardrails per agent kind.
Phase 5

Evaluators & seed data

  • Configure the 12 evaluators.
  • Generate ~6 months of synthetic traces per instance; backfill scores, including a deliberate MCP-scope-denial trace.
Phase 6

Rehearsal

  • Walk the demo narrative end-to-end as each persona; confirm every denial and identity-swap moment fires on cue.
